\paragraph{Sensitivity.}
The question here is whether our conclusions survive when the least realistic assumptions are replaced by real-world values. In short, the ranking of the set-ups survives every change we tested, but the size of the gaps does not: real pages widen it, while pricing in dollars and counting real human response time narrow it. Where the logs allow, we quantified each change instead of arguing it (scripts in the artifact).
\begin{itemize}
\item \textbf{Loan Estimate delay.} Without the 5\,s delay, a median of 2 model requests (range 1--4) and 9.8\,s would disappear from a website run, 4 requests and 17\,s from B, 1 request and 2.6\,s from C1, and none from the code-run set-ups. For those set-ups, however, the delay plus a 2\,s polling interval is 6.0\,s of their 22--23\,s, so without it they would take about 16--17\,s. No arm's request count moves by more than four, so the ordering in Tables~\ref{tab:main}--\ref{tab:realistic} stands. A real delay of hours to three business days cannot run in one session. It would also outlive the runtime's 1-hour prompt cache, so re-writing the context would add about \$0.33 (A) and \$0.14 (C1) to a run at list prices.
\item \textbf{Real pages and networks.} We loaded 13 public bank, lender and payroll pages with the same browser build. Taking each page navigation to cost the median DOMContentLoaded time (1.85\,s), each form post or download the median TTFB (0.67\,s), and each API call 0.3\,s (assumed), wall time rises by 31\% for websites (345 to 444\,s), 15\% for B-full, 14\% for C1, 36\% for C2 and 62\% for B-full-code. The ordering holds and the website gap widens; a low--high range of 0.67--5.49\,s per navigation gives $+$10\% to $+$79\% for websites. Real snapshots were 7.7$\times$ larger than the sandbox's, which on a rough upper estimate would nearly triple the website arm's tokens ($+$166\%).
\item \textbf{Price, not tokens.} At list prices a baseline run costs \$0.85 on websites, \$0.30 with four APIs, \$0.21 with the common API and \$0.01--0.02 with code. These figures are about half the runtime's own Sonnet cost estimates, and they put the website-to-common-API ratio at 4.1$\times$ rather than the 12$\times$ in tokens, because cache reads, which are most of the tokens, are cheap.
\item \textbf{Humans.} If each code, consent or approval took the 16.6\,s median for SMS codes and each question 60\,s, realistic-condition wall time would be 455\,s for websites, 214\,s for C1 and 148\,s for C2. Human time would then be most of every API set-up's wall time, and the website-to-code ratio would fall from 14$\times$ to 3.1$\times$.
\item \textbf{Concurrency.} Running up to six runs at once had no consistent within-arm effect on per-request latency.
\end{itemize}
